# 中英双语更新日志

将指定旧 tag 到新 tag 的实际变更直接写入 `assets/CHANGELOG_zh.md` 和 `assets/CHANGELOG_en.md`。中文、英文分文件维护，两种语言的条目、分类和顺序一致。默认完成文件编辑，不只在回复中提供草稿；用户另有输出要求时遵从用户要求。

## 确定范围与证据

- 从请求读取旧 tag 和新 tag；缺少任一端时，列出相关本地 tag 并询问，不擅自选择版本。尊重用户指定的输出位置与格式。
- 用完整 tag 引用验证两端指向提交，避免与同名分支混淆：

  ```bash
  git rev-parse --verify 'refs/tags/<old-tag>^{commit}'
  git rev-parse --verify 'refs/tags/<new-tag>^{commit}'
  git merge-base --is-ancestor 'refs/tags/<old-tag>' 'refs/tags/<new-tag>'
  ```

  替换占位符并正确引用 shell 参数。tag 缺失时说明情况；本地信息不足时可获取所需远端 tag，但不覆盖已有 tag。旧 tag 不是新 tag 的祖先时，说明分叉或顺序异常并确认范围，不默默倒置。
- 提交范围采用 `old..new`，不包括旧 tag 的提交，包括新 tag 的提交。代码差异比较两个端点，不使用三点 diff 代替端点差异：

  ```bash
  git log --reverse --format='%H %s%n%b' 'refs/tags/<old-tag>..refs/tags/<new-tag>'
  git diff --stat 'refs/tags/<old-tag>' 'refs/tags/<new-tag>'
  git diff --name-status 'refs/tags/<old-tag>' 'refs/tags/<new-tag>'
  ```

- 结合提交正文与相关 diff 判断实际行为，不只翻译 commit 标题。大型 diff 按功能或文件分批检查；对含糊提交、合并提交和重要用户行为深入核实。不要仅用 `--no-merges` 丢弃可能包含独立修复的合并提交。
- 只使用指定范围的证据，不把工作区改动、后续提交、未来计划或旧版已有功能写进本次日志。

## 筛选与写作

- **只保留用户感知明显的更新，整体尽量精简。** 优先记录主要新增功能、明显的体验改善、实际问题修复，以及影响用户的安装、兼容性或升级变化；感知不强的内容可以不写，不追求覆盖所有提交。
- 默认略过图标、按钮样式、尺寸、圆角、边距等视觉微调。只有解决明显的显示或操作问题时才保留，并简述解决的问题。
- 默认略过纯技术调整、内部重构、测试、代码格式、依赖例行更新、开发文档和 CI 维护，不额外设“技术调整”或“维护”分类凑内容。只有存在具体用户影响时才写入，并描述影响而非实现细节。例如，索引实现重构本身略过；如果证据表明它解决了索引卡住的问题，则写“修复部分图片索引时卡住的问题”。
- 将同一功能的多次实现、修复和后续调整合并为一条。遇到 revert，检查最终端点的实际状态；完全撤回的功能不能写成已发布能力。
- 每条尽量用一句简短的话表达一个核心变化，省略实现细节、操作步骤、附带能力和重复解释。相近修复可以合并，较小修复可以略过，避免内部术语、提交流水账和宣传式空话。用户明确要求详细或完整技术日志时，再按要求展开。
- 写完再压缩一遍：能用短句说清就不写长句，不为了展示工作量增加条目。例如写“桌面端支持拖入文件夹建立索引”，不展开拖放校验、提示或处理流程；写“修复相册索引恢复后的状态显示”，不逐项描述内部状态与计算逻辑。保留影响使用的重要限制和升级提醒。
- 性能收益、修复范围、支持平台、破坏性变更及数据迁移要求必须有证据。不要编造速度数字、issue/PR 编号、发布日期或升级步骤。重要结论证据不足时继续核实；仍无法核实时说明不确定性，不写成确定事实。
- 中文采用自然简洁的产品语言；英文按相同含义润色，避免逐字硬译。版本号、命令、文件名和产品名称保持原样。

## 输出与核对

先读取两份日志，按版本倒序插入新版本；已有同版本则就地更新，不重复追加，保留其他版本及用户提供的正文。

每个版本只使用 `## v版本号` 二级标题，并以单独一行 `---` 结束。新增、改进、修复、升级须知及英文对应分类使用 `**加粗**`，不用 `###` 或 `####`；分类与列表之间留空行，省略空分类。单语言文件不添加“中文”或“English”标签。中文文件结构：

```markdown
## <new-tag>

**新增**

- …

**改进**

- …

**修复**

- …

**升级须知**

- …

---
```

英文文件使用相同结构，分类为 `**Added**`、`**Improved**`、`**Fixed**`、`**Upgrade Notes**`。只有版本号使用标题语法；文件总标题如需保留也用加粗。

App 按当前语言读取对应文件（简繁中文均读取中文日志）。Release 由 `ci/extract_release_notes.dart` 自动提取对应版本正文：英文在前、中文在后，中间用 `---` 分隔，不标注语言，正文原样保留。`.github/workflows/release.yml` 自动追加提交对比链接，因此日志中不重复添加链接，也无需手动输入 Release 正文。

完成后用 `fvm dart ci/extract_release_notes.dart <new-tag> <临时输出路径>`（无 FVM 时用 `dart`）检查双语提取结果，确认目标版本在两份文件中各出现一次、正文非空、分割线完整，中英文内容对应且分类加粗。不为 CI 提取脚本新增单元测试。

提交范围为空或只有内部技术调整时，简短说明没有面向用户的更新，不填充虚构条目。交付前逐条核对证据，检查中英文是否一一对应，删除感知不强的条目并压缩冗长表述，确认没有重复条目、遗漏的重要升级影响或残留占位符。撰写日志本身不包含创建 tag、触发发布或发布 GitHub Release。
