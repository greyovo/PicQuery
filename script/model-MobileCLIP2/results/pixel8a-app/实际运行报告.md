# Pixel 8a：MobileCLIP2 正式 App 路径运行验证

2026-09-13，两个后端的正式运行代码已打入 Debug APK，安装到 Pixel 8a 并通过真机编码一致性测试和实际界面操作：仅索引 `PicQuery-Demo` 的 5 张公开图片，搜索 `dog` 显示 `dog1.jpg`，搜索 `astronaut` 显示 `astronaut.jpg`。TFLite 图像 4 线程、文本 2 线程的原生 XNNPACK 线程池均已确认存在。这里的“正式路径”指 App 主代码中的实现；本次没有验证 Release 构建或发布流程。

## 环境与配置

| 项目 | ONNX | TFLite |
|---|---|---|
| 应用 ID | `me.grey.picquery.mobileclip2.onnx` | `me.grey.picquery.mobileclip2.tflite` |
| 模型 | MobileCLIP2-S0 / dfndr2b | MobileCLIP2-S0 / dfndr2b |
| 精度 | 图像 FP32；文本动态 INT8 权重 | 图像 FP32；文本动态 INT8 权重 |
| CPU 线程配置：图像 / 文本 | 4 / 4 | 原生 XNNPACK 4 / 2 |
| Android 依赖版本 | ONNX Runtime 1.23.2 | LiteRT 1.4.1 |
| 库返回的版本字符串 | `1.23.2` | `2.20.0-dev0+selfbuilt` |

设备为 Pixel 8a / Tensor G3，序列号 `43231JEKB22129`，Android 17（API 37），4 KB 内存页；本次进程实际运行 `arm64-v8a`。两个 Debug APK 均包含 `arm64-v8a` 和 `armeabi-v7a`，这不代表已在 32 位设备验证。没有使用 GPU/NPU。两种模型与之前精度评测的资产保持一致，各 App 使用独立索引。

JNI 通过现有 `libtensorflowlite_jni.so` 的 XNNPACK API 创建 delegate，从官方默认 options 开始，只设置 `num_threads`。App 禁用 Java lazy delegate 的自动创建，再附加这个显式配置的 delegate；没有禁用 XNNPACK 计算或另带一份推理运行库。头文件 ABI 固定到现有 LiteRT 1.4.1。

每次查询的日志均返回 1 张结果，截图确认结果可见。这里验证的是 5 张图片中的两条查询，不是数据集识别精度或召回率评估；[有标签识别精度报告](../识别精度对比.md)单独记录了相关评测。

数值测试后，最终重打包只修正英文设置文案，模型和 JNI 实现未变；两个 APK 已重新安装。随后再次确认 TFLite 的 demo 索引仍保留、`astronaut` 搜索成功，设置页显示图像 4 / 文本 2 线程：[最终搜索截图](tflite-final.jpg)、[设置截图](tflite-settings.jpg)。完整编码测试对应文案修正前的构建，最终包没有重复该测试；最终 APK、原生库和模型哈希见 [验证记录](verification.json)。

| 单次 UI 操作中的日志计时 | ONNX | TFLite |
|---|---:|---:|
| 5 图批处理编码并保存向量 | 831 ms | 694 ms |
| 首次 `dog` 查询：完整查询变更到结果照片读取完成 | 1123 ms | 933 ms |
| 后续 `astronaut` 查询：完整查询变更到结果照片读取完成 | 258 ms | 217 ms |

计时边界：

- 批处理时间来自 `EmbeddingService` 的 `Batch cost`，仅包围 `saveBatchToEmbedding`：包含 `encodeBatch` 的预处理、调度、模型首次懒加载、推理与归一化，以及 ObjectBox 向量写入；不包含之前的相册查询、上游缩略图读取或之后的相册状态保存。不能将 694/831 ms 当成从点击按钮到索引完成的总耗时。代码见 [EmbeddingService](../../../../app/src/main/java/me/grey/picquery/domain/EmbeddingService.kt)。
- 搜索时间由同一日志中的完整 `onQueryChange: dog/astronaut` 到 `searchV2 photos re-orders` 的时间戳相减。它包含现有搜索流程的等待、翻译、候选编码、向量查询和结果照片信息读取；不包含结果帧实际绘制完成的测量。首条 `dog` 包含文本模型首次使用，后续 `astronaut` 使用已加载模型。
- 英文仍走中译英：本次日志的候选分别是 `Dog, dog` 和 `Astronaut, astronaut`，因此每次查询实际编码两个大小写候选。英文可以减少翻译影响，不能声称完全绕过翻译。

这是每个后端各一次手工 UI 运行，没有重复轮次、温控或持续负载协议，不能据此做速度排名。原始记录：[ONNX UI 日志](onnx-ui.log)、[TFLite UI 日志](tflite-ui.log)。

### 功能测试附带的计时

下表只描述该 instrumentation 协议：不启动 Activity，图像和文本 encoder 同时常驻；先各 10 次预热，再交替运行一次图像、一次文本，共各 50 个计时样本。图像路径包含预处理、调度与归一化，文本路径包含分词与归一化，输入 Bitmap 的初次文件解码不在计时范围。首次调用单独记录，可能包含资产复制和模型懒加载，不计入预热后统计。P50 使用 `statistics.median`，偶数样本取中间两项平均；P95 使用 nearest rank，即排序后第 48 项。

| App encoder 调用 | 首次调用 ms | 预热后 P50 ms | 预热后 P95 ms |
|---|---:|---:|---:|
| ONNX 图像 | 741.10 | 124.58 | 186.24 |
| ONNX 文本 | 919.49 | 61.23 | 103.83 |

| TFLite 文本 | 731.98 | 89.93 | 120.18 |

这组交替调用结果明显慢于此前[单塔线程探针](../pixel8a-tflite-diagnostics/诊断报告.md)。探针使用预处理好的张量并单独测量各塔；本表调用范围、调度方式及常驻会话条件不同。当前证据不足以给出差异的具体原因，不能直接扣减得到“预处理开销”，也不能将这些数字当作实际 UI 的持续速度或替代上面的单次 UI 记录。

## 构建及复现

需已有模型资产、Android SDK、NDK `29.0.14206865`、CMake `3.22.1`。Gradle 编译并打包 JNI 库，继续使用已有 LiteRT 1.4.1 依赖；官方头文件随源码固定，构建时无需下载。

从仓库根目录执行：

```powershell
.\gradlew.bat :app:assembleOnnxDebug :app:assembleTfliteDebug :app:assembleOnnxDebugAndroidTest :app:assembleTfliteDebugAndroidTest :app:testOnnxDebugUnitTest :app:testTfliteDebugUnitTest :app:ktlintKotlinScriptCheck :app:lintTfliteDebug
adb -s DEVICE_SERIAL install -r app/build/outputs/apk/onnx/debug/app-onnx-debug.apk
adb -s DEVICE_SERIAL install -r app/build/outputs/apk/tflite/debug/app-tflite-debug.apk
adb -s DEVICE_SERIAL install -r app/build/outputs/apk/androidTest/onnx/debug/app-onnx-debug-androidTest.apk
adb -s DEVICE_SERIAL install -r app/build/outputs/apk/androidTest/tflite/debug/app-tflite-debug-androidTest.apk
adb -s DEVICE_SERIAL shell am instrument -w -r -e class me.grey.picquery.feature.MobileCLIP2InstrumentedTest -e sampleCount 50 -e warmupCount 10 me.grey.picquery.mobileclip2.onnx.test/androidx.test.runner.AndroidJUnitRunner
adb -s DEVICE_SERIAL shell am instrument -w -r -e class me.grey.picquery.feature.MobileCLIP2InstrumentedTest -e sampleCount 50 -e warmupCount 10 me.grey.picquery.mobileclip2.tflite.test/androidx.test.runner.AndroidJUnitRunner
```

`DEVICE_SERIAL` 本次为 `43231JEKB22129`。仪器测试结果写入各 App 的 `files/mobileclip2_device_report.json`，可通过 `adb exec-out run-as <applicationId> cat files/mobileclip2_device_report.json` 读取。重复实验应将输出保存到新目录，不覆盖本报告原始记录。Windows 若因 TEMP 路径过长出现 JDK Unix domain socket 错误，可将当前终端的 `TEMP`、`TMP` 及 `JAVA_TOOL_OPTIONS` 中 `-Djava.io.tmpdir` 指向已存在且路径较短的 `build/java-tmp` 绝对路径。

实际界面复现：

1. 将 5 张公开图片放入手机 `Pictures/PicQuery-Demo`，完成媒体扫描后启动 App。图片来源与本地主机 fixture 见[模型说明](../../README.md#host-comparison)。如果启动后才加入图片，重启 App 进程以刷新相册列表。
2. 接受首次使用说明并授予照片访问权限。可在系统照片选择中只授权这 5 张；本次 TFLite 已验证该路径。另一后端已有权限时无需扩大或重设授权。
3. 首页“索引”→“添加相册”，仅勾选 `PicQuery-Demo`，确认“已选 5 张”，点击“索引”。等待底部“正在索引: 5 / 5”且“完成”按钮可点击。不要用引导步骤提前勾选作为完成证据。
4. 本次两个 App 都只有 demo 的 1 个已索引相册，因此日志的“Search from all albums”仅检索这 5 张。若已有其他索引，先用“范围”关闭“全部相册”，只选 `PicQuery-Demo` 并点“完成”；范围重启后需重新设置。
5. 搜索 `dog`，确认狗图；再搜索 `astronaut`，确认宇航员图。两个 App 各自完成索引后执行相同步骤。

相册初始化会枚举获准访问的 MediaStore 元数据，但模型编码只查询所选相册的 `BUCKET_ID`。当前没有自动全库编码任务；本次操作未索引用户其他相册。

构建及静态检查：

- 双变体主构建成功：1 分 37 秒，185 个任务，其中 73 个执行；两个变体各 13 个单元测试，共 26 个，失败、错误、跳过均为 0；`ktlintKotlinScriptCheck` 通过。[主构建及测试日志](build-parity.log)
- 英文文案修正后的最终构建成功：37 秒，102 个任务，其中 25 个执行。TFLite Debug Lint 为 0 errors、95 warnings、5 hints，不能称为零告警。[最终构建日志](build-final.log)、[验证汇总](verification.json)
- 只读 Detekt 已执行，`autoCorrect=false`，发现 27 条；项目配置 `ignoreFailures=true`，因此任务完成不代表没有问题。新路径 `TFLiteInterpreterSession.configureDelegate` 的 4 个早返回触发 `ReturnCount` 风格规则，保留早返回以便阅读，没有为消除该提示扩大重构范围。[Detekt 记录](detekt.txt)
- 原生实现经独立审查未发现阻塞问题，并核对现有运行库四种 ABI 中所需的四个 C API 符号；本次实机执行仍仅覆盖 ARM64。[验证汇总](verification.json)

复用已有运行库和模型资产，通过小型 JNI 桥接修正线程传递。此前 11 组诊断的原始 JSON、日志及 `production_app_changed=false` 保持历史含义；它们没有被改写为当前生产验证结果。

本机仍出现系统 16 KB 兼容提示。新增 JNI 库使用 NDK 29 并设置 16 KB ELF 对齐，但系统仍将其识别项标为 unknown，且 APK 中还有其他已有原生库；本次仅证明 4 KB 页设备运行通过，不能声称整包 16 KB 兼容性已解决。尚未验证 Release/R8、GPU/NPU、32 位设备、其他真机、长期连续索引与大相册负载，也没有在本次线程修正后重跑完整识别精度数据集。
